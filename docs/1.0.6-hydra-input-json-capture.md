# 1.0.6 六头蛇开局输入采集测试

> 2026-09-25 清理说明：本文是研究阶段的历史记录。文中提到的研究期工具（历史重放 `replay-observed`、首回合投影、选择器探针、动作脚本校验等）和 `out/` 下的研究证据已删除；离线引擎现在只保留 `json-convert` 与 `forecast` 两种模式，验证基线与现行实现见 [1.0.6 开局吞噬顺序推演](1.0.6-hydra-devour-forecast.md)。

本测试版的代理 ABI 为 4，build ID 为 `2026092403`。旧代理不能热重载成此版本；测试前须完全退出旧工具与 RAID 客户端，再用测试版重新启动。

六头蛇战斗开始后，代理从本局 `BattleContext.Setup` 读取原始 `BattleSetup`，从当前登录配置 `SharedModelManager.GameParameters.BattleSettings` 读取战斗参数。两者只调用游戏原有的 `JsonMain.ToJsonStr` 序列化，并通过独立的只读共享槽发布；不在游戏进程内执行原版 MessagePack 泛型反射、离线战斗或未来标记计算。每局最多尝试三次，间隔五秒；失败以原因码结束，不改动战斗动作。

`tools/observe_hydra.py` 从指定 PID 的共享槽只读取得 JSON。只在以下身份全部吻合时，才在采集目录 `replay-source` 保存 `battle-setup.json`、`battle-settings.json` 和 `capture-provenance.json`：本局 Setup GUID、种子、关卡、游戏账号 ID、六位英雄的库存 ID 与类型 ID，以及开局游戏快照的英雄类型和真实 `SlotId` 位置。点击开战时会刷新一次选队快照。即使身份校验未通过，也会在采集根目录保留有界的 `replay-source-candidate.json` 供离线排查；该文件不能直接作为已验证的重放输入。`--single-battle` 使记录器在观察到下一场战斗时停下，避免把自动重试并入原始样本。大 JSON 不写入逐回合日志。

原版离线进程的 `json-convert` 模式现在要求这两个 JSON 文件，并在无网络、无附加能力的 AppContainer 中用本机提取的原版序列化器分别转换为 `BattleSetup` 和 `BattleSettings` MessagePack。`tools/convert_hydra_replay_source.py` 先校验原件哈希，再核对隔离执行证据、账号、队伍、种子和战斗参数，成功后把两个 MessagePack 和转换报告写入 `replay-source/packed`。合成输入已经通过隔离转换；另有一次精确路径测试证明“单个 BattleSetup 序列化后套成列表”与原版直接序列化列表的 JSON 逐字节一致，且原版可完整回读六英雄身份。拿到真实完整输入也只代表具备开局重放条件，仍须核对运行库版本并逐动作对照真实 RNG 与标记后，才能声称未来千回合预测可靠。

2026-09-25 的 gafee 实测存于 `out/hydra-observation-20260925-060950-gafee-input-r2`。真实英雄栏位为 1–6，早期校验器只接受 0–5，故实时记录器把这份输入标为 `battle_setup_invalid`；原始候选文件完好。更新栏位校验后，`tools/recover_hydra_replay_source.py` 使用同局开局决策、独立账号快照和完整封口的日志恢复了已验证输入，另写 `recovery-status.json`，保留原始 `status.json` 的错误历史。原始 BattleSetup 29,532 字节、BattleSettings 2,420 字节；隔离原版转换后为 8,362 和 1,285 字节，两份转换报告哈希均通过。实测 `ActiveEngineVersion=11750`、`WarmupBattleRandomCount=10`、`MaxTurnsInBattle=1500`。这仍不表示已经能预测本场后续吞噬目标。
